# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

C++17 control/integration codebase for a **Cyton Gamma 1500** 7-DOF Dynamixel-servo robot arm, with an optional **NDI Polaris Spectra** optical tracker integration for pose capture/validation. Built with CMake. Currently developed and exercised on **Windows** against physical hardware (the Dynamixel arm on one COM port, the NDI tracker on another).

## Build

The configured generator is **NMake Makefiles**, which requires an MSVC developer environment on `PATH` — running `cmake --build`/`nmake` from a plain shell fails (`nmake` not found). Build from a **Developer Command Prompt for VS 2022**, or from another shell by sourcing `vcvars64.bat` first:

```bat
call "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Auxiliary\Build\vcvars64.bat"
cd build
nmake -f Makefile                        REM build every target
nmake -f Makefile test_ndi_single_tool    REM build a single target
```

To (re)configure the build directory from scratch:

```
cmake -S . -B build -G "NMake Makefiles" -DCMAKE_BUILD_TYPE=Debug
```

There is no test framework (no gtest/Catch2) and no lint config. `tests/*.cpp` are standalone `int main()` executables for manual, hardware-in-the-loop verification (see Architecture) — there is no "run all tests" command; each one is built and run individually against the physical robot/tracker, typically with interactive Enter-to-proceed prompts between motion steps.

## Dependencies (`external/`)

Three vendored dependencies live under `external/`, all committed as git submodule links (mode `160000`), but **only `ndicapi` has a corresponding `.gitmodules` entry**. `DynamixelSDK` and `trac_ik` are submodule references with no `.gitmodules` entry, so a plain `git submodule update --init --recursive` will not populate them.

- `external/DynamixelSDK` — ROBOTIS Dynamixel SDK; currently checked out and working.
- `external/ndicapi` — PlusToolkit's NDI Combined API C wrapper (github.com/PlusToolkit/ndicapi); the only properly-configured submodule.
- `external/trac_ik` — **currently an empty/uninitialized directory** in this checkout. The root `CMakeLists.txt` guards all TRAC-IK/IK targets (`test_trac_ik`, `test_cyton_ik*`) behind `if(EXISTS .../trac_ik_lib/CMakeLists.txt)`, so the build silently skips them until this is manually populated. The same existence-guard pattern gates the NDI targets (`test_five_pose_ndi_capture`, `test_ndi_single_tool`) on `external/ndicapi/CMakeLists.txt`.

## Architecture

- **`src/robot_calibration.{h,cpp}`** — the single source of truth for per-joint physical limits and zero points (`jointCalibrations`: one entry per motor ID 0–6 with `zeroTick`, `direction`, `minTick`/`maxTick`) plus the `radiansToTicks`/`ticksToRadians` conversions built on it. Every motor-facing program in `src/` and `tests/` goes through this table for safety clamping and unit conversion — joint limits are not duplicated per file.
- **`src/dynamixel_motor.{h,cpp}`** — `DynamixelMotor` wraps the Dynamixel SDK `PortHandler`/`PacketHandler` for the 7-joint arm: connect/torque/position/speed primitives; safety-checked single- and multi-joint moves (`moveJointSafely`/`moveJointsSafely`/`moveTrajectory`) that clamp against `jointCalibrations` before writing to the servos; electrical status snapshots (voltage/temp/load) for post-move diagnostics; `emergencyShutdown`.
- **`src/main.cpp`** — an early standalone demo that hardcodes `/dev/ttyUSB1` (a Linux device path). It predates the Windows-targeted `tests/*.cpp` programs (which use `COM4`) and is not kept in sync with them — treat it as a reference/demo, not the current entry point.
- **`tests/`** — not a unit test suite; each file is an independent hardware-in-the-loop program (radians/tick conversion checks, home-pose moves, IK target moves, NDI capture, etc.) meant to be built and run one at a time against the physical robot/tracker.
- **NDI integration** (`test_ndi_single_tool.cpp`, `test_five_pose_ndi_capture.cpp`) — both open a Polaris Spectra over serial via `ndicapi` and follow NDI's documented port-handle flow: `INIT` → `PHRQ` (tool type `"1"`/wireless is correct here — these are cable-less passive marker rigid bodies, not physically-wired tools, so `"0"`/wired fails with "handle has become unoccupied") → `PVWR`/`PVWRFromFile` (load a `.rom` geometry file) → `PINIT` → `PENA` → `TSTART` → poll with `BX` (binary transform request — see "Resolved issue" below; NDI Toolbox uses `BX` exclusively on this hardware, and the ASCII `TX` command never resolves markers here even though the port reports healthy). `.rom` file paths and the tracker/arm COM ports are hardcoded, machine-specific absolute paths — expect to update them per machine. `test_ndi_single_tool.cpp` also has built-in diagnostics (`freeAllExistingHandles`, `sweepVolumes`) that run automatically when zero valid transforms are seen, to help separate stale-port-handle causes from measurement-volume causes of a persistent `NDI_MISSING` result.

## Resolved issue: `ndiGetTXTransform()` always returned `NDI_MISSING`

**Status: RESOLVED 2026-07-23.** Root cause: our code polled transforms with the ASCII `TX:` command (`ndiTX()`/`ndiGetTXTransform()`). On this Spectra unit, `TX` never resolves markers — `NDI_MISSING` on every sample, forever — even though NDI Toolbox tracks the identical tool/ROM/position over the identical COM port without issue. Toolbox does not use `TX` at all; it exclusively uses the **binary `BX:` command**. Switching `test_ndi_single_tool.cpp`'s polling loop from `ndiTX`/`ndiGetTXTransform` (`double transform[8]`) to `ndiCommand(tracker_, "BX:%04X", mode)` + `ndiGetBXTransform`/`ndiGetBXPortStatus`/`ndiGetBXFrame` (`float transform[8]`) fixed it immediately: 24/100 samples came back `VALID` with real quaternion/translation data at the exact position that previously gave `0/100` on `TX`, and most of the rest failed only the strict `MAX_NDI_ERROR = 0.50` quality threshold by a small margin (`error` in the `0.50–0.55` range — ordinary measurement noise, not a tracking failure; worth loosening that threshold if a higher hit-rate is wanted).

Note that `ndicapi` has no `#define ndiBX(...)` convenience macro the way it has `ndiTX` (`#define ndiTX(p,mode) ndiCommand((p),"TX:%04X",(mode))` in `ndicapi.h`) — call `ndiCommand(pol, "BX:%04X", mode)` directly; `ndiCommandVA`'s `isBinary` check (`ndicapi.cxx` ~line 2781) detects the `"BX"`/`"BX2"` prefix and routes the reply through `ndiBXHelper()`, which populates the fields `ndiGetBXTransform()`/`ndiGetBXPortStatus()`/`ndiGetBXFrame()` read from. The reply-mode bits for `BX` are declared separately from the `TX`/`GX` ones in `ndicapi.h` (`NDI_3D_MARKER_POSITIONS 0x0008`, `NDI_NOT_NORMALLY_REPORTED 0x0800`, alongside the shared `NDI_XFORMS_AND_STATUS 0x0001` / `NDI_ADDITIONAL_INFO 0x0002`); Toolbox's captured mode was `0x080B` (all four combined), which is what the fixed code now sends.

**How this was found:** every API-reachable parameter (below) had already been ruled out with the device still reporting a healthy port and zero resolved markers — this was flagged as past the point of productive API-side guesswork, and the recommended next step was a passive USB capture of Toolbox's actual wire traffic to diff against our command sequence. That capture was obtained via **Wireshark + USBPcap** (see tooling note below) capturing NDI Toolbox's full connect → load ROM → track sequence on the Spectra's FTDI USB-serial adapter. `tshark`'s built-in `ftdi-ft` dissector confirmed the device/protocol; the raw bulk-transfer bytes (after stripping each IN transfer's leading 2-byte FTDI modem/line-status header) were reconstructed into the full ASCII command stream, which is what revealed Toolbox sending `BX:080B` repeatedly and never once sending `TX:`.

Secondary observation from the same capture, not yet needed since the `BX` switch alone fixed it: Toolbox also runs a `TSTART`→`TSTOP` priming cycle *before* requesting port handles, and a second one *after* loading both tools' ROMs but *before* `PENA`, ahead of the real final `TSTART`. Worth trying if a similar `NDI_MISSING`-style issue ever resurfaces and `BX` alone isn't enough.

**Tooling note — capturing serial/USB traffic on Windows without admin driver friction:** dedicated serial-port sniffers (HHD Software's Free Serial Port Monitor, PortMon) both failed on this machine due to Windows driver-signature enforcement blocking their kernel-mode drivers even with administrator rights, and a plain `.NET SerialPort`-based "monitor" (`gthvidsten/open-serial-port-monitor` on GitHub) turned out to just be an exclusive-access terminal, not a passive tap — architecturally incapable of monitoring a port while another program (Toolbox) holds it open. **Wireshark + USBPcap** worked: USBPcap installs as its own optional component during the Wireshark installer (a later step than the main "Choose Components" plugin/extcap-tools list, easy to miss — install it standalone from `desowin.org/usbpcap` if the bundled option doesn't appear), requires a **reboot** after install before its `USBPcapN` interfaces show up in Wireshark's capture list, and — once installed — needs no test-signing mode or other Windows security changes. To identify which `USBPcapN` interface corresponds to a specific USB device among several plugged in, start a capture and unplug/replug just that device's cable while watching for a burst of enumeration packets (`GET DESCRIPTOR`/`SET ADDRESS`) at that exact moment; the device's bus/address (e.g. `1.16.1`) is then stable for the rest of that session unless unplugged again. `tshark.exe` (bundled with Wireshark, e.g. `C:\Program Files\Wireshark\tshark.exe`) can filter/export fields directly (`-Y "usb.device_address==16 && usb.transfer_type==0x03"` for bulk transfers on a specific device) without needing the GUI.

## `test_five_pose_ndi_capture.cpp` post-fix improvements (2026-07-23)

After the `TX`→`BX` fix above was validated on `test_ndi_single_tool.cpp`, it was ported to `test_five_pose_ndi_capture.cpp` too (`requestBxUpdate()`/`tryReadToolFromCurrentBx()`/`ndiGetBX*`, `float transform[8]`), along with the same `ndiTSTOP(tracker_)` guard before `ndiINIT()` in `NdiTracker::initialize()` that `test_ndi_single_tool.cpp` already had (this file was missing it, and hit the documented "device stuck in tracking mode from an interrupted prior run" `PHRQ` error 12 as a result). Several other operational issues surfaced from there and were fixed:

- **`moveJointsSafely()` console spam** (`src/dynamixel_motor.cpp`) — the per-motor monitoring loop printed every ~100ms polling iteration, producing thousands of lines on a long/slow move. Now gated to print only every 10th iteration (`PRINT_EVERY_N_ITERATIONS`, ~once/sec) — affects every test that calls `moveJointsSafely`, not just this one.
- **`MOVING_SPEED`** in this file bumped `10 → 40` (matches the speed already used in `test_radians.cpp`) so moves finish faster and produce less log volume.
- **Windows Console QuickEdit-mode gotcha**: clicking into a PowerShell/cmd window (e.g. while a wall of text is scrolling) puts the console into "Mark" selection mode, which **pauses the process entirely** until Esc or a right-click deselects it. This looks exactly like a hang/freeze and was the cause of at least one "it just stopped" report during this work — press Esc first before assuming a real hang.
- **Per-sample rejection spam during capture** — `tryReadToolFromCurrentBx()`'s `printErrors` was `true` inside `collectBothTools()`'s retry loop, printing a line for every single rejected `BX` sample (routine, expected noise e.g. from someone briefly occluding the fixed tool). Set to `false`; the final thrown exception (if a pose never collects 30 valid pairs) still reports `movingInvalidCount`/`fixedInvalidCount`/`rejectedPairCount` so nothing diagnostic is lost.
- **Lab-foot-traffic tolerance** — this lab has frequent transient occlusion from people walking between the tracker and a tool. `collectBothTools()` now calls `waitForBothToolsVisible()` first (so a currently-blocked view is waited out *before* burning the timed collection budget), and both budgets were made much more generous: `waitForBothToolsVisible()`'s `STARTUP_ATTEMPTS` `100 → 600` (~30s at 50ms/attempt), and `collectBothTools()`'s `NDI_MAX_ATTEMPTS` `150 → 1000` (~20s at 20ms/attempt).
- **Interactive pause/skip + live per-tool status** — added while investigating the occlusion issue:
  - `'p'` pauses/resumes the current wait loop (`handleUserControls()` in the anonymous namespace, checked once per iteration via non-blocking `_kbhit()`/`_getch()` from `<conio.h>`); `'s'` throws `PoseSkippedByUser` (an empty struct, not `std::exception`-derived) to abandon the current pose without writing a CSV row, caught in `main()`'s per-pose loop (and, separately, at the top level around `ndi.initialize()`, since a skip during initial setup — before the per-pose loop's `try` exists — would otherwise be an uncaught-exception crash).
  - Each tool's `BX` status is classified (`classifyToolStatus()`) into `DETECTED`/`MISSING`/`OUT_OF_VOLUME`/`DISABLED`/`LOW_QUALITY` (this classification is display-only — the actual accept/reject decision in `tryReadToolFromCurrentBx()` is separate code using the same `MAX_NDI_ERROR` threshold, so `LOW_QUALITY` always means that poll was rejected) and printed only when it changes (`printToolStatusIfChanged()`), replacing the old periodic `printBxDiagnostics()` (now deleted, was called every 20 attempts regardless of whether anything changed).
  - A **persistent, unchanging** failure status (e.g. `MISSING` or `OUT_OF_VOLUME` that never clears no matter how long you wait) at a specific pose, reproducible on repeated runs with nobody nearby, indicates the arm's own geometry is blocking or misangling the moving tool's marker at that joint configuration — waiting longer never fixes this, since it isn't transient; the fix has to be physical (remount the marker, change the target pose, or reposition the Spectra). An **intermittent** failure that clears on its own is ordinary foot traffic.
- **Torque/Ctrl+C note**: this codebase has no `signal()`/`SetConsoleCtrlHandler` handler anywhere, so Ctrl+C just abruptly kills the process — none of the `catch` blocks or cleanup code run. This is not a safety problem in practice: Dynamixel torque-enable is a persistent state held autonomously by each servo's own firmware, not something that requires ongoing host communication, so the arm keeps holding its last commanded position regardless of whether the host process is paused (`'p'`) or killed outright (Ctrl+C). Torque only drops via an explicit disable call (normal end-of-run cleanup, `emergencyShutdown`) or actual power loss.

## Kinematic calibration (`calibration/calibrate_kinematics.py`)

**Goal:** correct mismatches between the URDF/forward-kinematics model and the physical arm's true geometry, using NDI-measured poses as ground truth, targeting **±0.5mm end-effector accuracy in MoveIt**. See `references/cyton_gamma_1500_trac_ik.urdf` (7 revolute joints, all `<origin rpy>` zero, ending in a fixed `virtual_endeffector` transform — a plain serial chain, no `trac_ik`/KDL dependency needed for FK).

`test_five_pose_ndi_capture.cpp`'s `TARGET_POSES` was expanded from 5 (all clustered within ~100 ticks of center — useless for calibration, since narrow-range poses can't separate a joint offset from a base/tool frame error) to 40 poses spread across each joint's safe tick range, except wrist_roll (joint 6, motor 6) which is kept narrow (±400 ticks around center) because large wrist_roll rotation turns the one-sided moving marker away from the Polaris. Widen joint 6's range only after empirically sweeping it (watch the `Moving tool: DETECTED/MISSING` status output) to find its real safe visibility window.

`calibration/calibrate_kinematics.py` fits a **19-parameter model**: one zero-offset correction per joint (7, radians — directly convertible to a `zeroTick` update for `robot_calibration.cpp`'s `jointCalibrations`), a small tool-frame correction (6: xyz+rpy, `virtual_endeffector` → moving marker), and the base-frame transform (6: xyz+rpy, base_link ↔ fixed marker frame — this one has no small-value prior, since we have no independent knowledge of where the fixed tool sits relative to the base, so unlike the other 12 it is bounded generously and **not** regularized toward zero). Uses `scipy.optimize.least_squares(method='trf', loss='soft_l1')` (bounds require `'trf'`; `'lm'` doesn't support them), position-primary residual with a de-weighted orientation term, held-out-pose validation, and a Jacobian-SVD/condition-number check to flag poorly-identified parameters.

**Known, provable, harmless ambiguity — not a bug:** `joint_offset[0]` (shoulder_roll) is *exactly* unidentifiable from the base frame's rotation, and `joint_offset[6]` (wrist_roll) from the tool frame's rotation, because each is the first/last joint in the chain with nothing rotationally between it and that free frame. Confirmed empirically during development: the relevant Jacobian singular value was bit-for-bit identical whether fit against 60 or 500 synthetic poses, which only happens if that direction gets zero information from pose data and is constrained purely by the (pose-count-independent) regularization term. This has **zero effect on predicted end-effector accuracy** (any split along that direction predicts identically) but means **joints 0 and 6's fitted `zeroTick` corrections must not be applied to `robot_calibration.cpp` in isolation** — without also consistently carrying the corresponding base/tool frame rotation into wherever FK is actually used downstream (MoveIt), that would apply half of a compensating pair and introduce a new error. Joints 1–5's offsets and both frames' translations are not subject to this and are directly trustworthy.

The script has a `--selftest` mode (synthetic ground-truth data, no hardware needed) — run this before trusting it on real data. It was developed and debugged using `uv run --with numpy --with scipy python calibrate_kinematics.py --selftest` (no other Python install was available on the dev machine at the time).

**Status as of 2026-07-24:** script written and self-test passing; the expanded 40-pose `TARGET_POSES` has not yet been run against physical hardware to produce a real `five_pose_ndi_capture.csv`, and the fitted parameters have not yet been fed back into `robot_calibration.cpp` or a MoveIt/URDF pipeline.

## Kinematic calibration: extended-model findings and a structural-degeneracy pattern (2026-07-28)

Hardware data collection did happen after the above status note: `TARGET_POSES` grew to 304 (original 40 → 190 → 200 new + 91 reused from an earlier batch → +13 deliberately orientation-diverse poses), captured via `test_five_pose_ndi_capture.cpp --quick-test` with CSV-append/resume support added so a Ctrl+C mid-run doesn't lose data. The current largest, cleanest combined dataset is `build/quick_calibration_test_combined_298.csv` (298 poses: 287 archived + 13 orientation-diverse; `_287pose.csv`/`_deduped.csv` are earlier archived subsets, kept for reference).

**A general structural-degeneracy pattern, beyond the joint0/joint6 base/tool-frame one already documented above:** for an *origin* translation correction (not the joint-offset rotation correction), joint `(i+1)`'s origin-component that lies exactly along joint `i`'s own rotation axis is **exactly** indistinguishable from joint `i`'s own origin-component in that same direction, for *every* possible joint angle — because a rotation never moves a point on its own axis. This is a hard mathematical identity, not a data-diversity limitation, and no amount of additional/better-diversified pose data can ever separate such a pair (verified numerically: the two parameters' Jacobian columns are identical to ~1e-11 across widely-varying random joint configurations). Confirmed instances (joint axes: 0=Z, 1=X, 2=-Y, 3=X, 4=-Y, 5=X, 6=Z):
- `elbow_pitch`-origin-Y ↔ `shoulder_yaw`-origin-Y — **found in practice** (a joint fit blew up to ~±249,000mm, nearly canceling, condition number ~3-4×10^8) and fixed by dropping `shoulder_yaw`'s Y-origin as a free parameter (fixed at 0, letting `elbow_pitch`'s Y absorb it) — this alone restored a healthy condition number (~964-976) with **zero change in RMS**.
- `shoulder_yaw`-origin-X ↔ `shoulder_pitch`-origin-X, `elbow_yaw`-origin-X ↔ `elbow_pitch`-origin-X, `wrist_pitch`-origin-Y ↔ `elbow_yaw`-origin-Y — predicted by the same rule and confirmed numerically (`calibration/diag_check_remaining_origin_gaps.py`), **not yet encountered in a fit** since `shoulder_pitch`'s and `elbow_yaw`'s origins have never been added as free parameters. Since `shoulder_yaw`-X, `elbow_pitch`-X, and `wrist_pitch`-Y are already free in the current model, adding `shoulder_pitch`'s or `elbow_yaw`'s *full* origin would silently re-trigger the same blow-up. Two components were confirmed (via the same numerical check, exactly orthogonal to everything already in the model) to be genuinely new/safe to add: **`shoulder_pitch`-origin-Y** and **`elbow_yaw`-origin-Z**. Not yet fitted/validated on real data as of this writing.
- Axis-*tilt* corrections (as opposed to origin) for joint 0/6 are **not** subject to the analogous degeneracy with `base_rpy`/`tool_rpy` — checked directly (`calibration/diag_check_tilt_degeneracy.py`, rank of `[rpy_columns, tilt_columns]` grows by the full 2 every time) — because tilt's effect scales with the joint's own rotation angle, unlike a fixed frame rotation. All 7 joints' tilts are safe to include.

**Root cause of an earlier apparent regression (the historical "~11.99mm" figure vs. current "~10.8mm"):** the ~11.99mm number came from `calibration/diag_validate_remaining.py` and its predecessors, which validated each new correction *incrementally* — hardcoding previously-found corrections (e.g. `ELBOW_PITCH_ORIGIN_DELTA`) as constants while leaving only the newest one free. This is a real methodology bug: it structurally cannot reveal a degeneracy between two parameters unless both are free *simultaneously*, so the elbow_pitch/shoulder_yaw-Y redundancy went undetected until everything was refit jointly, from scratch, on the larger datasets. The current ~10.8mm is not a regression — it's the same accuracy ballpark obtained honestly, with the redundancy actually found and removed rather than accidentally avoided. **Lesson: always jointly refit every free parameter from scratch when testing a new correction; never hold previously-found corrections fixed as constants.**

**Current best validated model (28 params: 19 base + `wrist_pitch` axis tilt (2) + `elbow_pitch` origin (3) + `shoulder_yaw` origin x,z-only (2, Y dropped per above) + `wrist_pitch` origin (3)):** RMS 10.80mm on the full 298-pose combined dataset, condition number 976 (healthy), held-out 80/20 split train=10.98mm/test=10.10mm, multi-start-robust (5 random starts → identical 10.801mm). Baseline (19-param-only, no extra corrections) on the same dataset is 23.03mm.

**Extended model — axis tilt for all 7 joints (not just `wrist_pitch`):** every joint showed a real, non-negligible tilt (`shoulder_roll` 3.04°, `shoulder_pitch` 3.75°, `shoulder_yaw` 4.22°, `elbow_pitch` 6.06°, `elbow_yaw` 4.47°, `wrist_pitch` 4.56°, `wrist_roll` 6.06°) — `wrist_pitch` was never a special case, it was just the one joint tested first. RMS drops to 8.98mm, condition number 1256 (healthy, no new degeneracy), held-out test=8.45mm < train=9.13mm (clean generalization). This recovers ~17% of the remaining error but confirms axis-tilt is *a* contributor, not the dominant remaining one — ~9mm still unexplained. Caveat: origin-correction values shift meaningfully once tilt is included (e.g. `elbow_pitch`-Y: 5.37mm → 14.26mm) — correlated with tilt, not exactly degenerate (condition number stays healthy), but treat the *exact* origin values as less stable than the overall accuracy number until re-checked on a different pose split.

**The two newly-identified "safe" origin additions were tested (2026-07-29) — dead end, recommend dropping.** Added `shoulder_pitch`-origin-Y and `elbow_yaw`-origin-Z to the 41-param model (19 base + 7 tilts + 3 origins) and jointly refit on the 298-pose set: RMS came back **identical to 3 decimal places** (8.980mm with vs. without), across all 6 multi-starts, with both new params landing on stable non-zero values (4.77mm, -3.71mm). No accuracy gain. Worse, several existing tilt values shifted substantially between the two fits (e.g. `elbow_pitch` tilt 6.06°→1.99°, `elbow_yaw` tilt 4.47°→1.70°) while RMS stayed frozen — the signature of a *soft* correlation (a linear combination of several existing tilt parameters spans nearly the same direction as the new params) that the earlier pairwise-orthogonality pre-check (`diag_check_remaining_origin_gaps.py`) couldn't detect, since it only tested each new parameter against individual existing ones, not against combinations. Lesson: pairwise orthogonality is necessary but **not sufficient** to guarantee a new parameter adds real information — the actual joint fit (RMS moves or it doesn't) is the real test. **Not adopted; dropped from the model.**

**A real optimizer-scaling bug was found and fixed while running the above test, worth knowing for any future fit in this file.** The ad hoc diagnostic scripts all used `scipy.optimize.least_squares(method="lm")` (unbounded, no internal parameter scaling) with a parameter vector mixing radians (~0.01-0.1 scale) and meters (~0.001-0.05 scale). On the 41→43-param extension this caused genuinely pathological behavior: one attempt ran 30+ minutes of CPU without finishing even one multi-start trial; a quick re-check produced an implausible 12-function-evaluation "convergence" and multiple physically-unrelated parameters sharing an identical Jacobian column norm (a diagnostic bug, not a real result — never trusted or reported as a finding). Root cause: unscaled mixed-unit parameters confuse `lm`'s step-size/convergence heuristics. Fix: `method="trf"` with `x_scale="jac"` (auto-normalizes by each parameter's own sensitivity) and generous physically-motivated bounds (wide enough not to clip any value seen so far — e.g. origins ±50mm vs. a ~14mm max observed, tilts ±15deg vs. a ~6deg max observed). This converged every trial cleanly in 15-40 function evaluations with consistent, repeatable results. **Recommend using `trf`+`x_scale="jac"`+bounds for any new joint-fit script added to this project going forward**, not raw unbounded `lm`.

**Joint gear-ratio scale error — refreshed with current rigor (2026-07-29), real improvement, adopted.** `calibration/diag_joint_scale_fit.py`'s original test (flagged stale above) was rerun as `calibration/diag_joint_scale_refresh.py`: one multiplicative scale factor per joint (`corrected_angle = measured_angle*scale + joint_offset`, distinct from the existing additive offset), added on top of the current best model (19 base + 7 tilts + 3 origins), using the `trf`/`x_scale="jac"`/bounds methodology above. Result: **RMS 8.98mm → 8.257mm**, all 6 multi-starts identical, condition number 1222 (healthy), held-out train=8.44mm/test=7.62mm (clean generalization, test even better than train). Fitted scales are small and physically plausible (all within ±2% of nominal 4096/2π ticks-per-radian): `elbow_yaw` +1.91%, `elbow_pitch` -1.14%, `wrist_pitch` +1.07%, `shoulder_pitch` +0.94%, rest under 0.5%. Cross-checked against the same correlation concern that killed the origin-param test above: some tilt/origin values did shift (e.g. `wrist_roll` tilt 4.02°→2.87°, `elbow_pitch`-origin-Y roughly halved), but — unlike that dead end — **RMS genuinely dropped** rather than staying frozen, which is the real distinguishing signal that this parameter is adding new information rather than just re-explaining the same signal under a different name. **Adopted as part of the current best model.**

**Current best validated model as of 2026-07-29 (36 params: 19 base + 7 axis tilts + 3 origin corrections + 7 joint gear-ratio scales):** RMS 8.257mm on the full 298-pose dataset, condition number 1222 (healthy), held-out train=8.44mm/test=7.62mm. Baseline (19-param-only) on the same dataset is 23.03mm.

**Joint coupling (cross-talk between joint pairs) — refreshed (2026-07-29), result inconclusive, not pursued further for now.** `calibration/diag_joint_coupling_refresh.py` reran the original correlation check (residual error vs. pairwise joint-angle products) using the current 36-param model's residuals on the full 298-pose set. Top raw correlations: `shoulder_roll*shoulder_yaw` -0.399, `shoulder_yaw*elbow_yaw` -0.336, `shoulder_pitch*elbow_pitch` 0.315. But `shoulder_yaw`'s own individual-joint correlation with error (0.424) is *stronger than any pairwise product*, and shoulder_yaw appears in most of the top pairs — a classic confound where a product inherits a strong single-joint's own signal without indicating real cross-joint coupling. `calibration/diag_partial_coupling_check.py` regressed error on shoulder_yaw alone and checked whether pairwise correlations survived against the *residual*: results were genuinely mixed, not a clean resolution either way — some pairs attenuated as expected if confounded (`shoulder_roll*shoulder_yaw` -0.399→-0.259, `shoulder_pitch*elbow_pitch` 0.315→0.133), but others *increased* (`elbow_yaw*wrist_roll` -0.252→-0.269, `shoulder_yaw*wrist_roll` 0.223→0.267) — the opposite of a pure-confound signature. Likely explanation: the pose set wasn't collected as an orthogonal designed experiment, so joint angles have their own correlation structure with each other, which a single-variable partial correlation can't cleanly separate. **Conclusion: this is ambiguous evidence, not a real lead on the level of tilt or scale.** A properly-controlled multi-variable check, or a full fitted coupling-matrix model (up to 21 new cross-terms — a much bigger, less-constrained parameter space than scale was, with its own likely identifiability problems given the pose set), would be needed to resolve it further. Not pursued for now given the ambiguity and cost; `shoulder_yaw`'s own unexplained residual (R²=0.180 against its own angle alone) is arguably the more tractable loose end if revisited — it suggests shoulder_yaw's own per-joint model (offset+scale+tilt+origin) still isn't fully capturing something *about that one joint*, which is simpler to chase than cross-joint coupling.

**Backlash test run and CONFIRMED (2026-07-29) — real, reproducible, several-mm effect in `wrist_pitch` (motor 5).** Methodology: `tests/record_hand_poses.cpp` was modified for a single-joint test -- the other 6 joints are torqued/locked (held exactly where they were) once at the start of the session, and only the joint under test (`TEST_JOINT_ID`, set to `5`) is left free to hand-pose, removing the other 6 as a variable. 4 poses recorded per the below/target/above/target sequence: pose 1 (below), pose 2 (target, arriving from below), pose 3 (above), pose 4 -- rather than relying on hand precision to return to "the same" tick, the servo auto-drives back to pose 2's exact recorded tick via a raw goal-position write + manual polling loop (bypassing `moveJointSafely()`'s built-in range check specifically for this narrow, pre-verified case -- see the code comment at that call site). These 4 poses were added to `tests/test_five_pose_ndi_capture.cpp`'s `TARGET_POSES` (indices 304-307) and `QUICK_TEST_POSE_INDICES`; **all 4 must be visited in that order** by the NDI-capture replay too, not just the 2 "target" ones -- otherwise the automated run wouldn't actually approach each target from the intended direction (the arm ends the recording session sitting right next to both targets already). Comparing the NDI-measured `moving_relative_fixed` position at poses 305 (target-from-below) vs 307 (target-from-above), run twice for reproducibility:

| | Run 1 | Run 2 |
|---|---|---|
| gap vector (dx,dy,dz) mm | (1.00, -3.04, 3.39) | (0.88, -2.77, 3.07) |
| gap magnitude | 4.66mm | 4.22mm |

Both magnitude (~4.2-4.7mm) and direction (same sign, similar proportions on all 3 axes) reproduced closely across two independent runs -- the signature of a real, systematic, direction-dependent effect, not measurement noise (which wouldn't reproduce direction this consistently). Confirmed this isn't just explainable by the small residual encoder mismatch either (the two runs' `wrist_pitch` landed 1-3 ticks apart each time -- via simple lever-arm geometry over the ~100mm remaining chain to the marker, that alone would only account for ~0.5mm, not 4-5mm).

**Caveat:** the other 6 joints were NOT held via the same torque-lock during the NDI-capture replay (only `moveJointsSafely()`'s ordinary ±10-tick tolerance) -- that lock only applied during the original hand-recording session that produced the tick values in the first place. The other 6 showed 1-2 tick differences between the two compared poses in each run (ordinary servo settling variance) -- small enough that they're very unlikely to explain a 4+mm gap on their own, but it means this isn't a perfectly isolated single-variable measurement. Also a single joint (`wrist_pitch`) and a single target-angle pair tested so far -- not yet repeated at a different target angle or on other joints.

**Conclusion: backlash is confirmed as a real, structural, several-mm contributor to the residual ~8mm** -- and, being direction-dependent, it is fundamentally NOT fixable by any static per-joint correction (offset/scale/tilt/origin all assume one fixed encoder-to-true-angle relationship regardless of approach direction). This is the strongest concrete lead of the four candidate error sources tested this session.

**Fix implemented (2026-07-29): unidirectional final-approach compensation in `src/dynamixel_motor.{h,cpp}`.** Rather than modeling backlash explicitly (would require tracking approach-direction as a new variable throughout the whole data/control pipeline and fitting an extra per-joint hysteresis parameter), the standard, simpler real-world fix was implemented: **every move now always finishes approaching its target from the same direction** (increasing tick value), converting backlash from an unpredictable direction-dependent error into an ordinary constant offset that the existing offset/scale/tilt/origin corrections already absorb. `moveJointSafely()` and `moveJointsSafely()` both gained a `compensateBacklash` parameter (default `true`, so every existing call site gets the fix automatically with no changes needed -- confirmed via a full project rebuild, all targets compiled cleanly). Mechanism: before the real move, any joint whose target is reached by *decreasing* its tick value first overshoots below the target (clamped to `jointCalibrations`' `minTick` if `enforceSafetyLimits` is set), via a recursive call with `compensateBacklash=false` to prevent infinite recursion; the joint then approaches the real target a second time, now guaranteed to be increasing. Joints already naturally approaching by increasing (or already at target) are untouched -- only joints needing correction pay the extra overshoot-move cost. `moveJointsSafely()` applies this per-joint (each of the 7 joints independently decided/corrected in one pre-pass) before the main synchronized move. An overshoot-failure (e.g. hitting the pre-existing stall-detector) is non-fatal -- it warns and proceeds to the real move anyway rather than aborting, since even an incomplete overshoot almost certainly still served its purpose. `BACKLASH_OVERSHOOT_TICKS` was tuned 40->20 after direct evidence (below) that a larger margin adds more of its own settling noise than it needs to.

**Validated (2026-07-29) via a direct, apples-to-apples comparison: same 49 poses (by `pose_id`), same 36-param model, same `trf`/`x_scale='jac'`/bounds fitting method, only the movement code differs.**

| | RMS | vs. old baseline |
|---|---|---|
| OLD (uncompensated) movement | 8.27mm | -- |
| NEW, 40-tick overshoot | 8.43mm | +0.16mm |
| NEW, 20-tick overshoot | 8.32mm | +0.05mm |

Cutting the overshoot margin in half cut the gap roughly in half too -- confirming the small RMS penalty comes from the overshoot's own extra settling cycle (each joint needing correction does two move-and-settle cycles instead of one, and the resulting scatter in other joints went from 1-2 ticks pre-fix to 3-8 ticks post-fix), not from backlash getting worse. At 20 ticks the difference from the old baseline is within measurement noise -- the fix is no longer costing anything meaningful in aggregate.

**A cross-dataset check** (fit on one dataset's 80%-train split, evaluate on the other dataset's matching held-out poses) showed a real but modest asymmetry: a model fit on the new (compensated) data predicted old (uncompensated) held-out poses ~1.4mm worse than its own held-out data, while the reverse direction showed no gap -- consistent with a small residual bias in the old data that the new data doesn't share, but not a large effect.

**Comparing the actual fitted tilt/scale/origin values (not just RMS) between old and new data** -- the most direct check of whether earlier-session corrections are real geometry or partly backlash artifact: joint scales are nearly identical (differences 0.1-0.3%), most tilts/origins shifted by under 0.15deg / ~1mm. Two exceptions stood out: `wrist_roll` tilt shifted 0.5deg and `wrist_pitch`'s Y-origin shifted ~1.2mm -- both are the two joints closest to where real backlash was independently confirmed (see below), so plausibly carry a bit more backlash-related contamination than the rest. **Conclusion: the tilt/scale/origin corrections fitted earlier this session are mostly real, validated geometry, not backlash artifacts in disguise** -- with `wrist_pitch`/`wrist_roll` specifically flagged as somewhat less certain than the others.

**Confirmed at a second joint: `elbow_pitch` (motor 3) also shows a real, substantial backlash effect**, via the same below/target/above/target hand-recorded test used for `wrist_pitch`. First attempt (loose tick-match, 11 ticks apart between the two "target" poses due to `record_hand_poses.cpp`'s then-15-tick `AUTO_DRIVE_TOLERANCE_TICKS`) gave ~16.4mm, contaminated by that mismatch plus elbow_pitch's longer lever arm to the marker amplifying it further. Redone after tightening `AUTO_DRIVE_TOLERANCE_TICKS` 15->4: the two target poses landed only 5 ticks apart, giving **~10.0mm** -- still well beyond what a 5-tick residual alone could explain (~2-3mm via lever-arm estimate), so a substantial real backlash effect remains. **This means backlash isn't isolated to one joint** -- it's a broader characteristic of this arm's servos/gear trains, though its *averaged* contribution across a diverse pose set (per the RMS comparison above) is much smaller than either isolated joint's worst-case test suggests, since most pose-to-pose transitions don't involve a full-range single-joint reversal the way these deliberately-adversarial tests do.

**Bottom line:** backlash is real, confirmed at two joints, the fix works correctly for whichever joint needs it, and once tuned (20-tick margin) it's neutral-to-slightly-positive at the aggregate calibration level while remaining the only thing in this project's toolkit that can address a fundamentally direction-dependent error. The earlier-session tilt/scale/origin fits are validated as mostly real geometry. Still not done: recollecting a full, broad calibration dataset (not just a 49-51 pose validation subset) under the fixed movement code and re-deriving final `robot_calibration.cpp`/URDF corrections from it.

**Remaining candidate sources of the residual ~8mm:** (1) joint-coupling — tested, ambiguous, not pursued further (see above); (2) **backlash — CONFIRMED, see above** (not yet quantified across other joints/angles, or corrected for in the model); (3) gravity/compliance (real non-rigid deflection, which no rigid-body model can represent by construction) — tested only with a crude, inconclusive correlation proxy; the standard published technique (elastostatic calibration: rigid links + a torsional-spring stiffness per joint, deflection proportional to gravity-induced torque) needs real link mass/center-of-mass data, which this project's URDF only has as placeholders -- a real, identified blocker, not yet resolved; (4) NDI's own relative-pose measurement accuracy between two independently-tracked ROMs — **now has literature backing, not just a guess**: published assessments put the Polaris Spectra's *single rigid-body* tracking error at ~0.64mm (passive mode) -- notably higher than the ~0.1-0.17mm single-*marker* trueness figure often quoted, and our measurement is the *relative* pose between two independently-tracked rigid bodies, so the realistic combined floor is likely ~0.9mm or higher (root-sum-square of two ~0.64mm uncertainties), not the ~0.5mm this project has used as its target throughout. **The ±0.5mm goal itself may need revisiting as optimistic for this measurement setup, independent of the robot's own calibration quality.** (5) **joint-angle-dependent (non-constant) kinematic error** — a formally recognized category in published robot calibration research, modeled as a Fourier series in each joint's own absolute angle (reflecting periodic gear-tooth-meshing effects); one study found a constant-offset model like ours explains only ~79% of measured error vs. ~97% with these terms added. Screened all 7 joints' current-model residuals against linear/quadratic/1-3-per-revolution periodic fits (`calibration/diag_fourier_screening.py`) — `shoulder_yaw` showed the strongest raw R² but was already known (from earlier in this file) to be a sparse-data artifact at extreme angles, not real. `shoulder_pitch` was the next candidate and, unlike shoulder_yaw, showed good data density across its *entire* range (13-57 poses per bin, no sparse tail) with a genuine smooth hump shape peaking near 0°. Added a 1/rev Fourier term to shoulder_pitch's own effective angle (`calibration/diag_shoulder_pitch_fourier_fit.py`) and validated properly: **RMS 8.257mm -> 8.187mm**, all 6 multi-starts identical, condition number 1223 (healthy), held-out test (7.71mm) better than train (8.34mm) -- a real, validated, if modest (~0.85%) improvement. Fitted amplitude 1.27deg, physically plausible for gear-mesh-type error. The other 5 untested joints all showed much weaker screening signal (R² under 0.08) and are not expected to yield a similar win.

**Research-backed context (2026-07-29):** a literature review surfaced that published kinematic-error taxonomies (rotating center offset, mastering, link length/assembly, pitch, strain-wave-gearing, out-of-plane, backlash) treat several of these -- including backlash itself -- as *also* varying periodically with a joint's absolute position (tied to gear-tooth meshing), not just a single constant gap as our current backlash fix assumes. Given the fix's aggregate effect is already confirmed small for this arm, refining it further is low priority. A more sophisticated ML-based hysteresis compensation approach exists in recent literature (Kriging surrogate + iterative feed-forward correction, IEEE Access 2024) but was judged not worth the added complexity given our own evidence of small aggregate benefit.

**Still unchanged from the original status note:** none of the fitted parameters (any model version above) have been fed back into `robot_calibration.cpp` or a real MoveIt/URDF pipeline yet. All results above are from an offline Python FK model compared against NDI measurements, not a live commanded-move-then-measure test. Also still applies: joint 0/6's *origin* and *joint-offset* (angle) corrections must not be applied in isolation from the base/tool frame (see the provable ambiguity note above) — this project now also has the analogous, non-degenerate axis-*tilt* correction for joints 0/6, which is safe to apply in isolation.

## External code review (2026-07-29) and its follow-ups

An external AI model was given the whole history above plus the core scripts and asked to find bugs/oversights rather than re-suggest already-ruled-out ideas. Its claims were independently verified line-by-line against the actual code (not just trusted) before acting on any of them — all four checked out exactly:

- **The held-out validation methodology was leaky.** Every held-out RMS reported above (e.g. the 8.187mm figure's train/test split) used a plain random 80/20 split (`diag_shoulder_pitch_fourier_fit.py`'s `rng.permutation`). But `TARGET_POSES` is recorded as continuous per-joint trajectories — consecutive entries differ by only tens of ticks on one joint — so a random split almost always puts a near-twin of each held-out pose in the training set. This is why test RMS kept coming out close to (or below) train RMS: the signature of a leaky split, not a well-generalizing model. **Confirmed with data, not just theory** — see the blocked-split section below.
- **The real-world IK round-trip validation (the ~13-15mm number) has a live confound and needs to be redone.** `test_five_pose_ndi_capture.cpp`'s quick-test path (poses 316-318, the actual IK validation poses) calls `moveJointsSafely(..., /*compensateBacklash=*/true, /*compensateOnlyJointIds=*/{3})` — i.e. only joint 3 (elbow_pitch) gets the backlash fix; every other joint, including wrist_pitch (motor 5, also confirmed to have real backlash), moves uncompensated during that specific test. The code comment there says "Revert to `{}` for a normal/production run" and this was never done. Until it is and the IK validation is rerun, the 13-15mm figure can't be cleanly attributed to servo tolerance alone — some of it may just be uncompensated backlash on the non-elbow joints. **Not yet fixed/rerun — do this before trusting that number again.**
- **Inconsistent, non-robust loss function.** `calibrate_kinematics.py` (the core script) fits with `loss="soft_l1"`, but `diag_shoulder_pitch_fourier_fit.py` (the script that actually produces every "current best" RMS figure in this file) uses plain unweighted least squares with no `loss=` argument at all — a handful of occlusion-degraded-but-not-quite-rejected poses (passing `MAX_NDI_ERROR=0.50` on average while still being noisier than typical) get full quadratic weight. Not yet switched to a robust loss and re-validated.
- **Tool-frame bounds disagree between scripts.** The core `calibrate_kinematics.py` bounds `tool_xyz`/`tool_rpy` to ±10mm/±10°, but every "current best" diag script (including the fourier-fit and coupling-fit scripts) silently widens this to ±100mm/unbounded. The core script, if run as-is on real data, would likely reintroduce a real error (a clipped tool rotation over the ~80mm tool lever arm can't be absorbed by the base frame). Not yet reconciled — anyone treating `calibrate_kinematics.py` as canonical should know the diag scripts quietly diverge from it here.
- **`visibleMarkerCount` hardcoded to 4** in the capture code — re-confirmed as genuinely cosmetic (only ever written to CSV / used in a `min()`, never enters the fit). Fully ruled out as a contributor, not just deprioritized.

### Blocked-split validation confirms the leak, and finds a second thing: a localized bad region

`calibration/current/diag_blocked_split_and_residuals.py` re-validated the 36-param+Fourier model (the one behind the 8.187mm figure) two ways on the full 298-pose `quick_calibration_test_combined_298.csv`:

1. **Blocked 8-fold CV** (contiguous `pose_id` ranges as folds, so each held-out block is a real contiguous trajectory chunk, not scattered rows with neighbors leaking into training): pooled out-of-fold test RMS = **11.85mm**, meaningfully worse than the 8.187mm full-fit / random-split figure this file has been reporting throughout. Confirms the leak was real. Per-fold test RMS ranged 6.57-11.58mm for 7 of 8 folds — except **fold 5 (pose_id 191-227): train=6.60mm, test=20.48mm, gap=+13.88mm**, wildly worse than every other fold.
2. **Per-pose residual histogram** from the full-dataset fit: not simply "a few outliers" — a genuinely broad spread (p50=6.16mm, p75=9.51mm, p90=11.54mm, p99=20.23mm, max=25.83mm). But the worst individual poses cluster tightly by `pose_id` (192-196, 204-206) rather than scattering randomly, and that cluster sits exactly inside fold 5's range.

Checked NDI measurement-quality columns (`moving_camera_error`, `fixed_camera_error`, `moving_relative_fixed_error`, visible-marker counts) for pose_id 188-210 directly: **completely normal** — 4/4 markers visible on both tools throughout, error values in the ordinary 0.40-0.56 band, nothing flagged. So this is not a tracker-occlusion/quality problem. Checking `target_tick` columns instead: this exact pose_id range is where **multiple joints move simultaneously by large amounts** (several joints swinging hundreds-to-thousands of ticks together across a handful of consecutive poses). This matters because the earlier joint-coupling investigation (`diag_joint_coupling_refresh.py`/`diag_partial_coupling_check.py`, called "ambiguous, not pursued further" above) tested correlation across the *whole* dataset, potentially diluting a real effect that only shows up when multiple joints move together.

**Correction (2026-07-31): the "unlike most of the dataset, which is single-joint sweeps" claim above, and its repetition in several diag script docstrings, was wrong and never actually verified — caught via external review, checked directly, confirmed wrong.** Counting joints moved (>10 ticks) per consecutive-pose transition across the full dataset: median **5.0** joints per transition, mean 4.90, and **88.9%** of all 297 transitions move 4 or more joints simultaneously. Multi-joint motion is the overwhelming norm in this dataset, not a special property of the fold-5/pose_id-191-227 region. This sharpens rather than resolves the fold-5 puzzle: since "multiple joints moving together" describes ~89% of the whole dataset, it cannot be what specifically makes fold 5 worse than the other 88.9%-multi-joint transitions elsewhere — whatever is special about that region has to be something more specific than joint-count alone (see the external-feedback section below for a more specific candidate signature).

**Practical conclusion: blocked/contiguous-range splits, not random splits, are now the correct held-out validation methodology for this project going forward.** Every prior held-out number in this file that used a random split should be considered optimistic.

### Joint-coupling model fit (2026-07-29) — real, validated improvement; adopted; does not fully explain fold 5

Given the fold-5 finding, `calibration/current/diag_joint_coupling_model_fit.py` re-tested joint coupling properly this time: instead of a post-hoc correlation check, it adds actual coupling correction terms into the FK model itself and refits, using the same `trf`/`x_scale="jac"`/bounds methodology as every other validated addition in this file. Kept deliberately small (3 terms, not the full 21-pair matrix floated earlier as having "likely identifiability problems") — just the top 3 pairs the original screening had already flagged as strongest: `shoulder_roll×shoulder_yaw → shoulder_yaw`, `shoulder_yaw×elbow_yaw → elbow_yaw`, `shoulder_pitch×elbow_pitch → elbow_pitch` (downstream joint absorbs the correction — this was originally justified in this file as "motivated by the Cyton's cable-driven joints," but that claim was never verified and turned out to be wrong: the URDF (`references/cyton_gamma_1500_trac_ik.urdf`) shows plain `revolute` joints with no `<mimic>`/`<transmission>` tags, and the C++ code maps one dedicated motor per joint — no mechanical coupling is documented anywhere in this repo. **Retracted 2026-07-30.** The coupling finding itself is still real (confirmed by an actual refit showing RMS genuinely drop, not by the cable hypothesis), but *why* it physically happens is back to unknown — plausible alternatives for an independent-servo arm include structural/frame flex, cross-axis bearing loading, or the terms partly absorbing a geometric URDF placeholder error rather than a true mechanical effect).

**Result — real and validated:**
- Full-dataset RMS: **8.187mm → 6.874mm**, identical across 4 multi-starts, condition number 1214.6 (healthy, no new degeneracy).
- Fitted coefficients are modest and well inside their ±0.3 rad⁻¹ bounds (+0.0018, +0.0219, -0.0165 rad⁻¹) — not bound-clipped artifacts.
- Blocked-CV pooled test RMS: **11.85mm → 9.87mm**.
- Fold 5 specifically: **20.48mm → 17.08mm** — a real, meaningful improvement, confirming coupling was genuinely part of what hurt that region.

**But fold 5 is still the worst fold by far** (other folds: 5.89-10.89mm test RMS even with coupling added; fold 5: 17.08mm, gap +11.58mm vs. +0.79 to +4.32mm elsewhere). So coupling is adopted as a real, validated model addition — but it's only *part* of the fold-5 story, not all of it. Remaining candidates for the rest: a genuine data-coverage gap (this specific multi-joint-simultaneous pose type is rare and concentrated in one narrow, non-interspersed `pose_id` band rather than spread through the dataset, so it's structurally vulnerable to falling entirely into one held-out block), a 4th/different coupling pair not yet tested, or a session-specific issue unique to that batch of poses.

**Current best validated model as of 2026-07-29 (53 params: prior 38 + 3 joint-coupling terms):** full-dataset RMS 6.874mm; honest blocked-CV pooled test RMS 9.87mm. **The blocked-CV number, not the full-dataset-fit number, is the one to trust and quote going forward.**

### A 4th coupling term was screened for and ruled out (2026-07-30) — dead end, confirms fold 5 isn't more coupling

Since fold 5 stayed the worst fold by far even with the 3 confirmed coupling terms, `calibration/current/diag_coupling_screening_round2.py` screened all 18 remaining joint-pair products (of the 21 possible) against the 3-term model's own residuals, on both the full dataset and restricted to just the fold-5 region — the same methodology upgrade (residual-from-current-model, region-restricted) that made the original 3 terms identifiable when the whole-dataset aggregate check had called coupling "ambiguous."

**No clean candidate emerged — the screen surfaced the same confound pattern instead.** Within fold 5, several *individual* joints correlate with residual error almost as strongly as any product does: `shoulder_pitch` alone (-0.613), `shoulder_roll` alone (-0.580), `wrist_roll` alone (+0.544) — versus the top product candidate, `shoulder_roll×elbow_yaw`, at only 0.632. A product barely stronger than its own strongest constituent's individual correlation is the signature of riding on that joint's main effect, not independent coupling — exactly the pattern that made the original whole-dataset screening ambiguous for `shoulder_yaw`.

Per this project's own established rule (correlation alone doesn't decide it — the actual fit does, see the two-origin-term dead end above), the top 2 candidates were tested anyway with a real refit (`calibration/current/diag_coupling_round2_test.py`): `shoulder_roll×elbow_yaw → elbow_yaw` and `elbow_yaw×wrist_roll → wrist_roll`, added on top of the validated 3-term model (55 params total). **Result: a clean dead end.**
- Both new coefficients fit to essentially zero (+0.0006, -0.0007 rad⁻¹ — 30-40x smaller than the smallest confirmed term), regularized away for lack of independent signal.
- The 3 original coefficients didn't move at all (+0.0018→+0.0019, +0.0219→+0.0219, -0.0165→-0.0165 — unchanged to 4 decimal places).
- Full-dataset RMS: 6.874mm → 6.873mm (noise). Fold 5: 17.08mm → 17.11mm (unchanged, if anything marginally worse). Pooled blocked-CV: 9.87mm → 9.93mm (unchanged).

**Conclusion: joint coupling is now fully exhausted as a lead.** 3 real terms were found and adopted; nothing more is there, checked both by correlation screening and by an actual refit with the confound-diagnostic (do RMS and existing parameters move) applied both ways. Fold 5's remaining ~17mm is not a coupling problem.

This sharpens rather than closes the fold-5 question: since coupling is ruled out, and fold 5's poses are specifically the ones with the largest simultaneous multi-joint excursions in the dataset, the two remaining candidate explanations are (a) a genuine data-coverage gap (this configuration type is rare and clustered, not spread through the dataset) or (b) **real elastostatic link deflection** — large multi-joint excursions plausibly correspond to the arm's most extended, most gravity-loaded configurations, which is exactly the regime where non-rigid sag (a real physical effect no rigid-body correction of any kind, coupling included, can represent) would be largest. This is circumstantial, not proof, but it's a genuine reason to weight the still-unimplemented elastostatic/gravity lead (blocked on missing real link mass/CoM data) higher than before, rather than assuming fold 5 is just a coverage problem solvable by collecting more poses.

### Data-coverage hypothesis ruled out; orientation and wrist_roll coverage also ruled out (2026-07-30)

Three follow-up checks, all with real data rather than reasoning alone, closed off every "it's just a data-diversity gap" explanation tried so far:

- **Trajectory-aware, round-robin-diversified folds** (`calibration/current/diag_trajectory_aware_folds.py`): detected 46 real trajectory segments from tick-jump boundaries and round-robin assigned them across 8 folds, spreading the fold-5 bad region (pose_id 191-227) across 7 of 8 folds instead of one. Result: **no change** — pooled test RMS 9.86mm (vs. 9.87mm before), bad-region test RMS 17.37mm (vs. 17.08mm before). Diversifying which poses train alongside which doesn't matter; those specific poses are equally badly predicted regardless of what else is in training. This rules out fold arrangement/coverage as the explanation — it's a property of the poses themselves, not the split.
- **Wrist_roll coverage** (`calibration/current/diag_wrist_roll_coverage_check.py`): a concern that wrist_roll's documented narrow design range (±400 ticks) might be an untested-extrapolation blind spot invisible to any cross-validation on this dataset. Checked directly: wrist_roll actually spans **340-3753 ticks** across the real 298-pose dataset (near the servo's full range) — the "kept narrow" note earlier in this file describes an early design intention that was clearly widened in later collection rounds and never updated. Every one of the 8 folds' training set covers 100% of that fold's own test range in wrist_roll. Ruled out — not a coverage gap, and even if it were, no current split could show it either way.
- **True orientation-outlier holdout** (`calibration/current/diag_orientation_holdout_test.py`): the sharpest version of the coverage concern — every split tried (random, blocked, trajectory-aware) had training data spanning the test set's own range in whatever dimension mattered, so none of them could reveal a genuine orientation-extrapolation failure even if one existed. Fixed by identifying the 21 poses that are genuine orientation outliers (median pairwise angular distance >140° from every other pose — confirmed these have almost no close neighbors anywhere else in the dataset) and training purely on the other 277, testing only on those 21 truly-unseen orientations. Result: test RMS 10.52mm, only modestly above the general blocked-CV baseline (9.87mm) — **orientation coverage is not a significant error source**. (Raw orientation diversity across the whole dataset also turned out to be large — median pairwise distance 47°, full 353° range on roll — contrary to an earlier impression that only a handful of poses were orientation-diverse.) Notably, the *worst* poses within this outlier set (pose_id 209-212, 14-17.6mm) are the same poses sitting inside the fold-5 bad region — not a separate problem, just the same hard poses showing up from a second angle, consistent with them being the arm's most extended/awkward configurations rather than evidence of an orientation-specific gap.

### Lumped gravity/elastostatic deflection model (2026-07-30) — real, validated improvement; adopted; still doesn't fully close fold 5

`calibration/current/diag_gravity_deflection_lumped.py` tested the cheap version of elastostatic calibration that doesn't need real per-link mass/CoM data (still missing, still blocking the rigorous version): gravity torque is linear in the unknown mass-moment terms, so instead of measuring real masses, it approximates all downstream mass as one equivalent point at the current end-effector position and fits one deflection coefficient per joint (7 new params) from the existing NDI position data — the geometric "gravity moment arm" term is computed purely from the FK chain already in the model, no new hardware needed. Validated against literature (see below) rather than improvised: identifying elastostatic/gravity parameters from external position measurements alone, no torque/tension sensor, is a real published technique with reported successes (e.g. 45% end-effector error reduction using only camera-based position measurements in one industrial-robot study).

**Result — real and validated:**
- Full-dataset RMS: **6.874mm → 5.876mm**, identical across 4 multi-starts, condition number 1124.4 (healthy, actually improved from 1214.6).
- Fitted coefficients are physically plausible in pattern: `elbow_pitch` (+0.2216 rad/m) and `elbow_yaw` (+0.1145 rad/m) dominate — the mid-chain joints carrying the most downstream mass at the largest lever arms — while `wrist_roll` fits to ~0, consistent with that joint's rotation axis having little downstream lever arm left to generate gravity torque about itself.
- The 3 coupling coefficients barely shifted (+0.0018/+0.0219/-0.0165 → +0.0032/+0.0221/-0.0156) — gravity and coupling aren't confounded with each other; both are adding independent information.
- Blocked-CV pooled test RMS: **9.87mm → 8.91mm**.
- Fold 5 specifically: **17.08mm → 15.86mm** — a real but modest improvement (~7%), **not** a fold-5-specific win. Fold 5 remains dramatically worse than every other fold (now 5.16-10.74mm elsewhere vs. 15.86mm there; gap +11.12mm vs. +0.41 to +5.34mm elsewhere).

**Adopted as a real aggregate improvement, but it does not resolve fold 5.** The lumped single-point-mass approximation is doing real work overall, but either it's too crude to capture whatever's specifically happening in the fold-5 configurations (a proper per-link mass/CoM model might do better, still blocked on real hardware mass data), or something beyond gravity/elastostatic is still contributing there. Since every coverage-based explanation is now ruled out (see above) and gravity only partially explains it, the standing literature-backed recommendation for what's left is a data-driven residual model (Gaussian Process or neural network fit directly on joint-configuration → position-error over the same dataset) layered on top of the physical corrections already found — the standard "second stage" in published robot calibration methodology for exactly this situation, with reported improvements in the literature going from ~1.8mm/2mm mean/max error down to ~0.1-0.2mm this way. Not yet attempted here.

**Current best validated model as of 2026-07-30 (60 params: prior 53 + 7 lumped gravity-deflection terms):** full-dataset RMS 5.876mm; honest blocked-CV pooled test RMS 8.91mm.

### GP residual layer (2026-07-30) — real, validated improvement across every fold

`calibration/current/diag_gp_residual_layer.py` implemented the literature-backed "second stage" recommended above: per fold (same 8 contiguous blocks used throughout), fit the 60-param physical model on train only, compute its residual *vector* (dx,dy,dz, not just magnitude) on train, fit one Gaussian Process per output dimension (RBF + per-joint ARD length scales + WhiteKernel noise term, standardized joint angles as input, TRAIN mean/std only — no leakage), then add the GP's predicted correction to the physical model's held-out test predictions.

**Result: every single fold improved, not just some.** Pooled blocked-CV test RMS: **8.91mm → 7.81mm** (~12%). Per fold: 5.16→4.05, 6.83→5.20, 6.31→5.78, 8.00→7.39, 7.07→5.68, 15.86→**14.54** (fold 5), 10.74→9.74, 6.56→4.37mm. Fold 5 improved too (~8%) but remains by far the worst fold. A nearest-neighbor-distance diagnostic (standardized 7D joint-angle space) shows fold 5's test poses do sit somewhat farther from their nearest training example (median 1.56) than most folds (0.74-0.98), consistent with sparser local support there — but folds 3 and 6 show similarly elevated distances (1.43, 1.53) without being nearly as bad, so sparse coverage alone doesn't fully explain fold 5 either.

**Checked and ruled out: fold 7's unusually low error (4.37mm) is not a data-duplication artifact.** Given the dataset is a merge of several collection batches ("91 reused from an earlier batch" per the combined-298 history), a real concern was that a near-duplicate pose from a different batch could land at a non-adjacent pose_id and leak into training — a form of leakage blocked-CV (which only guards against *adjacent*-trajectory near-twins) would never catch. `calibration/current/diag_duplicate_pose_check.py` checked directly: computed every pose's true nearest neighbor (Euclidean, all 7 joint angles in tick-equivalent units) across the *entire* dataset, not just within-fold. Zero poses (out of 298) have a suspiciously close (<30 ticks), non-pose_id-adjacent nearest neighbor — fold 7's nearest-neighbor distances (130-500 ticks) sit squarely within the dataset's normal range (p10-p75: 212-392 ticks). Fold 7's low error is a genuine "this region of joint-space is easier" effect, not leakage — and this also validates that the 298-pose merge didn't introduce hidden duplicate-pose contamination anywhere else either.

**Current best validated as of 2026-07-30: honest blocked-CV pooled test RMS 7.81mm** (physical model 8.91mm + GP residual layer). Running tally: 9.87mm (post-coupling) → 8.91mm (post-gravity) → 7.81mm (post-GP), ~21% cumulative, each step smaller than the last (a normal diminishing-returns shape, not a sign of an imminent breakthrough).

### Backlash overshoot margin (`BACKLASH_OVERSHOOT_TICKS`) — RESOLVED, dead end, closed (2026-07-30)

Following on from the confirmed backlash finding earlier in this file: back-calculating the *true* tick-domain backlash gap from the already-confirmed mm-scale hand-test measurements, using the FK model's own lever-arm distances (wrist_pitch pivot-to-tool ~100-140mm, elbow_pitch ~250-300mm), implied true gaps of roughly **21-29 ticks** (wrist_pitch) and **~22-26 ticks** (elbow_pitch) — i.e. at or above the 20-tick overshoot margin already in `dynamixel_motor.cpp`, not "comfortably larger" as that code's own comment claimed (that claim had never actually been checked against the confirmed measurements). This looked like a plausible, concrete explanation for why the original 20-tick fix showed a roughly neutral aggregate result.

Tested directly: `BACKLASH_OVERSHOOT_TICKS` bumped 20→35 (comfortably clearing both implied gaps) and re-run through the exact same 49/51-pose old-vs-new comparison methodology used to validate the original fix (same 36-param model, same `trf`/bounds fitting). **Before running it, a review of the existing 40-tick data point caught the flaw in this reasoning**: 40 ticks should, by the same calculation, *already* comfortably exceed both implied gaps — yet 40 ticks (8.43mm) had already performed *worse* than 20 ticks (8.32mm), not better, which directly contradicts "undersized margin" as the explanation (if true, more margin should have helped, not hurt).

The 35-tick run confirmed this: **8.392mm** — worse than both 20 ticks and the uncompensated baseline (8.27mm), landing exactly between the already-tested 20-tick and 40-tick results. All three tested margins (20/35/40) now show a clean, monotonic RMS increase with overshoot size, and none ever beats the uncompensated baseline. **Conclusively rules out "undersized margin"** — the correct explanation is that once the overshoot exceeds the true gap, correction benefit plateaus while settling-noise cost keeps scaling with overshoot size, so any margin at or above the minimum sufficient value just adds pure cost with no further benefit. `BACKLASH_OVERSHOOT_TICKS` reverted to 20 (the best of the three tested values). **This specific parameter should not be re-litigated without new evidence** — three real data points now agree.

This also reinforces the earlier conclusion in this file that the backlash fix's *aggregate* benefit across a diverse pose set is small — not because backlash isn't real (it's confirmed at two joints via direct hand tests), but because most real pose-to-pose transitions in typical use don't involve the kind of full-range single-joint reversal that made those isolated hand tests show 4-10mm.

(Two housekeeping notes from testing this: `tests/test_five_pose_ndi_capture.cpp`'s `QUICK_TEST_POSE_INDICES` and the `compensateOnlyJointIds` argument at the quick-test call site had been left overwritten/restricted for the separate IK-validation and motor-3-isolation experiments — both reverted 2026-07-30 to the 51-pose evenly-spaced set and full-joint (`{}`) compensation for normal/production runs. `MOVING_SPEED` was also restored 15→40, since the slow speed was specific caution for the IK-validation's numerically-inverted, never-hand-verified poses, which doesn't apply here.)

### A real hardware validation tool, a fit-script identity check, and the reduced-DOF breakthrough (2026-08-04/05)

**Built a real hardware validation tool: `--validate` mode in `test_five_pose_ndi_capture.cpp`.** Distinct from every prior mode in this file, this one is explicitly about testing genuine forward-kinematics/calibration accuracy against **new, not-in-training** points: it reads a CSV of `tick_0..6,predicted_x/y/z_mm`, moves the arm to each tick target, measures the actual NDI position, and logs the deviation — live and to `validation_results.csv` (`achieved_tick_*` and `max_tick_error` columns were added after the fact, see below). Predictions are generated offline by a new Python companion, `calibration/current/gen_validation_predictions.py`, which fits the 60-param model on a chosen dataset and evaluates it at caller-supplied tick targets — explicitly **not** meant to reuse poses already in the fit data, since that would just re-measure training fit, not generalization.

**Important distinction clarified during this work, worth remembering:** `--validate` (given known ticks, predict-then-measure) tests **forward-kinematics/calibration accuracy**, not inverse-kinematics accuracy. A true IK round-trip test requires a *desired Cartesian target*, numerically inverting it to ticks, then comparing the *actual* measured position against the *original desired target* — not against a re-derived FK prediction (which would trivially match if IK converged). The existing `TARGET_POSES` 316-318 IK-validation poses are the closer analogue, but have their own known confound (`compensateOnlyJointIds` restricted to `{3}` there, never reverted) that was never re-run cleanly.

**A second, deeper limitation surfaced from a user question and is worth stating plainly: everything measured by NDI in this whole project — every RMS figure in this file — is *relative*, not *absolute*, accuracy.** The measurement itself is the moving marker's pose relative to the fixed marker; the model's `base_frame` transform (fixed-marker → `base_link`) is a **freely fit parameter with no independent ground truth**, deliberately unregularized because there's no independent way to know where the fixed marker sits relative to the robot's true mounting base. Practical implication for a MoveIt end-use: the joint-level corrections (offset/scale/tilt/backlash/gravity/coupling) transfer directly into a URDF and don't need the tracker present at runtime — that part is real and durable. The fitted `base_frame` does **not** transfer, since it's anchored to a temporary calibration-time measurement rig, not to anything present during real task execution; `base_link`'s physical location for MoveIt is just wherever the robot is bolted down, and relating perception/task targets (camera, fixtures, etc.) to that frame is a separate, still-open calibration problem this project's NDI work was never going to solve.

**Repeatability floor measured for the first time all project — genuinely good news.** Built by alternating between 2 (then 8) points many times each and comparing the raw `actual_x/y/z_mm` measurements against *each other*, not against any model prediction (a materially different question from accuracy — precision vs. accuracy, a tight-but-off-center cluster vs. a loose-but-centered one). Finding: a real, consistent **"first visit" effect** — the first arrival at a point after moving from elsewhere lands ~0.5-1.3mm away from where every subsequent repeat visit settles — followed by genuinely tight steady-state repeatability, **~0.1-0.2mm** (max ~0.20mm from centroid across repeats). **This means the arm's own mechanical repeatability is not the bottleneck for sub-1mm accuracy** — it's well under 1mm once past the first-visit transient. The remaining gap is in the calibration model and/or execution precision, not unfixable hardware jitter. The first-visit effect itself is unexplained (settling/relaxation after a large excursion is a plausible guess) and not yet investigated further.

**Compliance-margin/slope/punch investigated as a likely contributor to the tick-tracking issue, not yet acted on.** `dynamixel_motor.h`/`.cpp` already has full read/write support (`readComplianceMargins`/`writeComplianceMargins`/`readComplianceSlopes`/`writeComplianceSlopes`/`readPunch`/`writePunch`, correct AX-series Protocol 1.0 addresses 26/27/28/29/48) and a `reset_compliance` tool that verifies factory defaults (margin=1, slope=32, punch=32) are in effect — confirmed nothing in the active codebase currently sets these away from default; the stalling behavior is happening at stock settings. Cross-checked against the real ROBOTIS AX-12A documentation: Compliance Margin (default 1 tick) is a dead zone with zero corrective torque; Compliance Slope (default 32, one of 7 discrete steps 2/4/8/16/32/64/128, higher = softer) sets torque *proportional* to remaining error; Punch (default 32, range 32-1023) is a minimum-current floor below which "the motor won't activate at all." **Mechanism, well-documented not speculative:** near a small residual error under real load (gravity, friction), the slope-proportional torque demand can legitimately fall below Punch's floor, at which point the servo generates zero corrective torque and simply stops — exactly the observed stable "Error: 7, forever" symptom. Every validation run's `max_tick_error` column exceeding `MOTOR_TOLERANCE_TICKS` (values 3-12 vs. tolerance 5) on essentially every point is consistent with this happening routinely, not as an edge case — and the single worst point in both physical validation runs (6.7-6.9mm deviation) also had the worst `max_tick_error` (11-12 ticks) of any point measured. **Caution carried forward from this project's own history: an earlier attempt (2026-07-29) to fix this by changing slope and punch together, aggressively, across presumably all joints caused audible vibration and was reverted** (`reset_compliance` exists because of that incident) — any retest needs to be one parameter, one joint, small step, verified vibration-free before expanding, not a repeat of that approach. **Not yet tested or fixed.**

### Original investigation log (kept for reference — the causes below were all correctly ruled out; the actual root cause, found later via packet capture, is the `TX`/`BX` command choice above, which none of these individually address)

As of 2026-07-22, both passive rigid-body tools (`8700339`/`8700449` ROMs) track successfully in NDI Toolbox at the same physical position, but `test_ndi_single_tool.exe` / `test_five_pose_ndi_capture.exe` never got a valid transform — `ndiGetTXTransform()` returned `NDI_MISSING` on every sample, indefinitely, even though the port handle looked completely healthy (`status=0x31` = `TOOL_IN_PORT | INITIALIZED | ENABLED`, no `OUT_OF_VOLUME`/`PARTIALLY_IN_VOLUME` bits) and the frame counter kept incrementing (the TX round-trip itself was fine).

The following causes were each tested directly and ruled out — **don't re-try these without new evidence**:
- **Physical position / line of sight** — Toolbox tracks successfully at the exact same position without the tool being moved.
- **ROM/marker-geometry mismatch** — the identical `.rom` file was manually loaded in Toolbox and worked.
- **Concurrent Toolbox session** — Toolbox was fully closed before running the C++ test.
- **Measurement volume** — `SFLIST:03` shows exactly two characterized volumes on this Spectra; both were explicitly selected via `VSEL` and tracking restarted on each — both gave `0/20` valid transforms. (The sweep code that proved this has since been removed from `test_ndi_single_tool.cpp` now that the negative result is settled and documented here.)
- **Stale/leaked port handles** — `PHSR` with `NDI_ALL_HANDLES` (see `freeAllExistingHandles()`) showed 0 pre-existing handles before our own `PHRQ`, so it isn't a previous run's handle squatting on the marker.
- **`PHRQ` tool type wired vs. wireless** — `tool="0"` (wired) fails outright with error 45 (`0x2D` = "all handles have been allocated" per the real error table — see correction note below), confirming these cable-less tools must use `tool="1"` (wireless/virtual-SROM) — already correct in the code.
- **`PENA` enable mode** — tried both `NDI_STATIC` and `NDI_DYNAMIC`; identical result either way.
- **`PINIT` warning text** — its raw reply is a clean `"OKAY"` with no wavelength-mismatch warning appended, even though `Param.Default Wavelength.Return Warning=1` (warnings enabled) on this device.
- **IR sensitivity** — `Param.Tracking.Sensitivity` was read (`4`, mid-range on the device's 1=highest–7=lowest scale) and explicitly set to `1` (highest) via `SET:Param.Tracking.Sensitivity=1`, confirmed changed via a follow-up `GET`; identical `0/100` result. **The device was left at `1` (not restored to `4`) after this test** — the one-time `SET` call has since been removed from `test_ndi_single_tool.cpp` (it was permanently mutating device state on every run), but the hardware itself may still be at sensitivity `1` until explicitly set back.
- **Hardware alerts** — `Info.Status.Alerts=1048576` (bit 20, "System battery fault" — the backup battery for the bump sensor/clock, unrelated to optical tracking) is the only active flag; nothing tracking-relevant is set. **Physically confirmed**: the Spectra has a constantly flashing orange light, which per the manual's Table 4-2 LED indication column is exactly this alert's documented signature ("System battery fault" → Error LED: flashing, Status LED: on) — so this is a real, ongoing hardware fault on this unit (likely needs the internal backup battery replaced), not a transient/misread status. Still not the cause of `NDI_MISSING` though: this alert's documented "System Response" is only to set the diagnostic-pending status bit — unlike e.g. a temperature fault, whose documented response explicitly states "the system will not return tracking data." No such statement exists for the battery fault, and it's scoped to the bump sensor/clock, not the camera/tracking pipeline. Worth mentioning to NDI support as additional context regardless, since it's an active fault on the exact unit in question.
- **IR illuminator rate** — `Param.Tracking.Illuminator Rate` defaulted to `0`; `GETINFO` revealed the real enum (`20,30,60` Hz, selected by 1-based index, not literal Hz — `SET:...=20` fails with error 54/`0x36` = "user parameter value set is out of valid range", confirming the index form). Set to index `1` (20 Hz) via `SET:Param.Tracking.Illuminator Rate=1`, confirmed changed via `GET`; identical `0/100` result. **Left at index `1` (not restored to `0`)** on the device.

Notably `Param.Tracking.Available Volumes=Pyramid,Extended Pyramid` confirms these are the two standard stock volumes (not a broken/custom config), and clears up why `Selected Volume` reads `0`: the named `GET`/`SET` parameter is 0-indexed while the legacy `VSEL` command is 1-indexed — not a real anomaly.
- **Marker wavelength vs. volume compatibility (checked directly against the real manual, with hard data, not just absence of an error)** — `PHINF`'s `markerType=44` decodes (per the actual Polaris API Guide Rev. 5, `NDI_MARKER_TYPE` reply bit layout: bits 0–2 = wavelength, bits 3–7 = marker type) to **870 nm, Passive sphere** (`44` = `0b00101100` → wavelength bits `100` = 870 nm, type bits `00101` = Passive sphere). Named `GET`/`SET` parameter commands (undocumented as macros in this vendored `ndicapi`, but supported directly via raw `ndiCommand(tracker_, "GET:Param.X")` calls — see `tryQuery()`/`queryTrackingParameters()`) work fine on this unit's firmware (`007.000.011`).

**Documentation note — read the real manual directly, not summarized fetches.** Earlier research in this investigation used `WebFetch` against `usermanual.wiki/Pdf/PolarisAPIGuide.378985072/help`, which runs everything through a lossy summarizing model and repeatedly truncated mid-section. The actual PDF (`usermanual.wiki/Pdf/PolarisAPIGuide.378985072.pdf`, "Polaris Application Program Interface Guide - Revision 5", 198 pages) can be downloaded and read directly/grepped as text via `pdftotext` (poppler-utils; on Windows, `oschwartz10612/poppler-windows` on GitHub ships portable no-install-needed binaries — useful since this environment has no admin rights to install PDF tools normally). The function's actual behavior is correct; only its source comments (and my earlier reading of them) were misleading. Trust the real manual's Table 6-1 (page 167) over those comments when decoding a raw `ndiGetError()` value.

- **`TX` request mode / `NDI_ADDITIONAL_INFO`** — `ndiGetTXMarkerInfo()` in the vendored library appears to have a real indexing bug (`pol->TxInformation[2 + marker]` uses `marker` as a row index into the per-*handle* array instead of a byte offset within the current handle's own row — it computes the correct handle index `i` via a lookup loop but then never uses it), and the per-handle buffer it writes into (`char TxInformation[NDI_MAX_HANDLES][12]`) is smaller than the current manual's documented max size for that reply block (22 chars: 2 tool-info + 20 marker-info). Rather than fix/work around that getter, we tested whether requesting it at all was interfering with tracking: simplified `ndiTX()` to request only `NDI_XFORMS_AND_STATUS`, dropping `NDI_ADDITIONAL_INFO` and the bit our header mislabels `NDI_FRAME_NUMBER` (current manual: frame number is unconditionally part of the default reply already; that bit, `0x0008`, actually requests "3D positions of markers on tools" instead). Identical `0/100` result — ruled out. (Kept simplified in `test_ndi_single_tool.cpp` regardless, since it's simpler and avoids the buggy code path, even though it wasn't the cause.)

- **Serial-break hardware reset, prompted by an audible clue** — the user noticed the Spectra audibly beeps twice when NDI Toolbox connects, but stayed silent when our code ran. The manual's "Resetting the System with a Serial Break" section documents exactly this beep ("Upon initialization, the SCU emits one beep, and the Position Sensor emits a distinctive 2-beep sequence") as a result of a **hardware serial break**, not the plain `INIT:` ASCII command our code was sending — so it was very plausible Toolbox performs a serial-break reset on connect and we never had. `ndiRESET(p)` in this vendored `ndicapi` is already exactly this (`#define ndiRESET(p) ndiCommand((p),NULL)`; passing `format == NULL` to `ndiCommandVA` resets comm to 9600/8N1, flushes, calls `ndiSerialBreak()`, and waits for the device's `RESETBE6F` confirmation) — a ready-made function we'd simply never called. Added `ndiRESET(tracker_)` right after opening the port and before `INIT` in `test_ndi_single_tool.cpp`. Result: the reset genuinely worked at the protocol level (clean `"RESET"` reply, and critically the frame counter restarted near zero — `frame=399` vs. the 40,000+ seen in prior runs — confirming a true hardware reset per the manual's description of the frame counter). The device beeped **twice as much as Toolbox** (two full 2-beep sequences, one from the break and apparently another from the subsequent `INIT:` on the freshly-reset device, vs. Toolbox's single sequence) — audible confirmation this path did *more* reset activity than Toolbox, not less. **Still identical `0/100`, `status=0x31`, `MISSING` result.** This rules out "insufficient device reset" as conclusively as this line of investigation can — kept `ndiRESET()` in the code since it's a correct, low-cost robustness improvement (matches documented warm-boot recovery practice) even though it wasn't the cause.

**Bottom line (historical):** at the time, every parameter reachable via the API (position, ROM, sessions, both volumes, stale handles, tool type, enable mode, sensitivity, illuminator rate, alerts, wavelength/volume compatibility, `TX` request mode) had been individually tested and ruled out — several with hard decoded proof, not just absence of an error — with the device consistently reporting a healthy port and zero resolved markers. This exhaustive (and correct, as far as it went) elimination is *why* a packet capture was pursued next — see the resolution at the top of this section for the actual root cause (`TX` vs `BX`), which none of these ruled-out causes could have found on their own since it's a difference in which command is sent, not in a parameter passed to it.

**Device state left modified by this investigation** (not restored): `Param.Tracking.Sensitivity=1` (was `4`), `Param.Tracking.Illuminator Rate` index `1`/20Hz (was `0`). Neither caused nor fixed the issue; worth restoring to original values (`4` and index `0`/0Hz respectively) now that the real fix is known, if matching factory defaults matters going forward.

**Operational note (unrelated to the above, still relevant):** interrupting a run mid-`TSTART` (e.g. Ctrl+C) can leave the *device itself* stuck in tracking mode, separate from the OS COM port. Symptom: the next run's `ndiOpenSerial` may fail, and/or the one after that gets `PHSR`/`PHRQ` error 12 (`0x0C`, "command invalid for current mode" per the NDI API guide — not what the vendored `ndiErrorString()`'s string table would suggest due to an off-by-one indexing bug in that function; trust the raw numeric `ndiGetError()` value and the guide, not that function's text). Fixed by an unconditional `ndiTSTOP()` before `ndiINIT()` at the top of `initialize()`.
